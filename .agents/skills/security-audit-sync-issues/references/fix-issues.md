# 修正 Issue に反映する

確定（独立検証済みで、[監査成果物の照合](issue-sync.md#1-監査成果物を照合する) で反映対象とした所見）が1件以上あるときに読む。security-audit-verify-items も、調べ直して確定にした問題の修正 Issue をこの規則で作る。登録先（`REPO_HOST`・`REPO`・`ISSUE_REPO`）と既存 Issue の全ページの一覧は、[登録先と既存 Issue を確かめる](issue-sync.md#2-登録先と既存-issue-を確かめる) で用意したものを使う。

## 1. 同じ根本原因の Issue を特定する

- `security-audit:summary-id` のある集約 Issue を除き、ラベルの有無を問わず修正 Issue を探す。監査用区画に記録された `fingerprint` と `fingerprint-alias` を完全一致で照合する。一致する識別子がなければ、根本原因・破られる権限や信頼の境界・原因のコード・必要な修正を比べる。タイトル・重大度・行番号は照合の手掛かりとして使う。同じ実行の所見も根本原因ごとにまとめる。

| 照合結果 | 進め方 |
| --- | --- |
| 同一性が不明、または開閉を問わず候補が複数 | 候補の URL と理由を報告して保留する |
| 同じ根本原因の Issue が1件に決まり、開いている | その Issue の新旧を次の手順で確認する |
| 同じ根本原因の Issue が1件に決まり、閉じている | 再発候補として URL を報告し、再オープンと新規作成を保留する |
| 一致も重複の疑いもない | 根本原因ごとに1件作成する |

- 修正 Issue を書くのは、集約 Issue と同じリポジトリだけにする。根本原因が共有ライブラリやインフラなど別のリポジトリにありそうなときも、作り先は変えず、本文にそのことを書く（[修正 Issue の書式](issue-templates.md#修正-issue) の「対応の範囲」）。

## 2. 既存 Issue を更新できるか確かめる

- 既存 Issue の監査対象 SHA を `OLD_SHA` とする。監査対象として明記された値を使い、短縮 SHA の場合は対象リポジトリで一意に解決できる場合だけ完全な SHA にする。`OLD_SHA` と `NEW_SHA` は、対象リポジトリのコミットに対応する完全な SHA で比較する。
- 報告確定日時はオフセットや `Z` を含む値を実際の時刻に換算して比較する。タイムゾーンの異なる実行も同じ基準で比較し、文字列の大小や日付だけで順序を決めない。オフセットを確認できない日時は不明とする。

| 比較結果 | 更新する内容 |
| --- | --- |
| SHA が異なり、対象リポジトリで `git merge-base --is-ancestor "$OLD_SHA" "$NEW_SHA"` が成功 | 今回の所見・`NEW_SHA`・確認済みの報告確定日時を反映する |
| SHA が異なり、今回が古い・履歴が分岐・コミットの比較が不能 | 上書きを保留する |
| SHA が同じで、確認済みの報告確定日時が今回の方が新しい | 今回の所見と報告確定日時を反映する |
| SHA が同じで、報告確定日時の一方または両方を確認できない | 同じ根本原因と確認できた場合に、未登録の別名だけを追加できる。既存の所見・SHA・報告確定日時を保持する。追加する別名もなければ、新旧不明による保留として記録する |
| SHA が同じで、報告確定日時が同じか今回の方が古い | 同じ結果で差分がなければ変更なしとする。古い結果や食い違う結果は、理由を報告して保留する |
| 既存の監査対象 SHA が不明 | 更新案を示して保留する |

- 新しい監査結果を受理したら、所見の文章が同じでも、次回の比較に使う SHA と確認済みの報告確定日時を記録する。今回の報告確定日時が不明なら、今回の区画では `completed-at` を省く。
- 更新する場合は最初の `fingerprint` と登録済みの別名を保持し、今回の値が未登録なら別名として一度だけ追加する。

## 3. 修正 Issue を作成・更新する

### タイトルと本文を書く

- タイトルは `[critical] 問題を具体的に表すタイトル` の形式にする。接頭辞には、独立検証済みの `severity.impact.score` の値をそのまま使う。値は `critical`・`high`・`medium`・`low`・`informational` の5段階とする。成立条件と到達可能性は本文に記載する。
- Cloudflare の成果物では公式の深刻度を使う。本文の「問題と影響」に、タイトルの影響評価と総合深刻度（`severity.overall_severity`）を書式どおりに併記し、検証済みの根拠を示す。
- 同じ根本原因の問題は同じ基準で評価する。同じ根本原因で深刻度に差があれば、成立条件と影響の違いを本文に書く。
- [修正 Issue の書式](issue-templates.md#修正-issue) に従って書く。図は処理の流れが込み入ったときだけにし、図の内容を文章でも説明する。
- コードへのリンクは、監査対象 SHA に実在するパス・行を確認し、その SHA で固定する。GitHub で参照できない箇所はパスと行を示す。集約 Issue も含め、秘密・実データ・攻撃ペイロード・詳しい再現手順・監査成果物の全文は掲載しない。

### 書き込みと結果を確かめる

- 書き込む前に、新規作成なら既存 Issue を全ページ取得し直して重複を判定する。更新なら `gh issue view "$NUMBER" --repo "$ISSUE_REPO" --json number,url,state,title,body,labels` で最新状態を取得し、手順 1 と 2 の判定をやり直す。
- 更新は、監査用区画を一意に特定でき、人が追記した本文を保てる場合に行う。区画外の本文・担当者・既存ラベル・既存の親 Issue を保持する。今回の所見を受理できた場合は、タイトルの先頭にある深刻度だけを今回の影響評価に合わせ、残りの文言を保持する。先頭に深刻度がなければ付ける。別名だけを追加する場合はその行だけを追記し、タイトルを保持する。区画や追記箇所が不明なら更新案を集約 Issue に記録して保留する。
- 本文を端末のファイルに書く。作成・更新の直前に [登録先の確認](issue-sync.md#2-登録先と既存-issue-を確かめる) と同じ `gh repo view` で登録先の条件を再確認し、条件を満たせば該当するコマンドを実行する。既存本文と差分がなければ本文の更新を省く。本文が空なら作らない。

  ```bash
  gh issue create --repo "$ISSUE_REPO" --title "$TITLE" --body-file "$BODY_FILE"
  gh issue edit "$NUMBER" --repo "$ISSUE_REPO" --body-file "$BODY_FILE"
  ```

- タイトルに差分がある場合だけ、更新コマンドに `--title "$TITLE"` を付ける。タイトルだけを変更する場合は `gh issue edit "$NUMBER" --repo "$ISSUE_REPO" --title "$TITLE"` を使う。
- 作成・更新後は `gh issue view` で URL・状態・本文・タイトルを確かめ、fingerprint ごとの反映結果を `issue_sync` に保存する。成否が不明なら、再試行前に全ページの一覧と対象 Issue を読み直す。既存 Issue の編集権限がなければ、その URL と更新案を集約 Issue に記録して保留する。今回の監査に載らなかった Issue の状態はそのままにする。

### 自動修正できるか確かめる

今回作成した修正 Issue と、反映対象と確定した開いている修正 Issue を判定する。反映後の本文と採用済みの所見を使い、別名だけを追加した場合は既存の所見を使う。リポジトリの関係者や Issue の作成者のコメントも確認する。次をすべて満たす場合は `agent:autofix` の対象とする。

- 修正する箇所・守るべき仕様・修正完了条件が明確で、実装方法を既存の規約の範囲で選べる。
- PR のベースブランチでも所見と修正方針が当てはまることを確認できる。ベースの指定がなければ、[登録先の確認](issue-sync.md#2-登録先と既存-issue-を確かめる) の `defaultBranchRef` で確認した既定ブランチを使う。調べたコミットがベースの先頭だった場合は、ラベルを付ける直前にベースの今の先頭（`git ls-remote origin <ベース>`）を確かめ、同じならこの条件を満たす。違うときだけ、根拠と修正方針がなお当てはまるかを差分で確かめる。
- 回帰テストや既存のチェックなど、開発環境で修正完了条件を確かめる方法がある。
- 修正・検証・PR 作成までに、仕様の選択、未決の権限や互換性の判断、本番操作や人の追加承認が要らない。

判断に必要な情報が足りない場合は、不足している情報を集約 Issue に記録する。すでに `agent:autofix` が付いている Issue に人の判断が必要と分かった場合は、ラベルを保持したうえで、理由と URL を集約 Issue に記録する。判断の理由は修正 Issue の「対応の範囲」にも書く（ラベルの有無は書かない）。

## 4. ラベルとサブ Issue

- 修正 Issue に `agent:security-audit` を付ける。`agent:autofix` は手順 3 の条件を満たす修正 Issue に付ける。ラベルの確かめ方・作り方は [ラベルを確かめて付ける](issue-sync.md#ラベルを確かめて付ける) に従う。
- `agent:autofix` を付ける直前に、Issue の状態・本文とコメント全ページを読み直す。開いており、最新の本文とコメントでも自動修正の条件を満たす場合だけ付ける。コメントは `gh api --hostname "$REPO_HOST" --paginate --slurp "repos/$REPO/issues/$NUMBER/comments?per_page=100"` で取得する。
- 集約 Issue の番号 `SUMMARY_NUMBER` が決まり、その Issue が開いていれば、反映結果が作成・更新・変更なしの修正 Issue を集約 Issue のサブ Issue にする。サブ Issue の親は1つだけなので、先に `gh api --hostname "$REPO_HOST" "repos/$REPO/issues/$NUMBER/parent"` で親を確かめ、結果は次のどれかとして詳細の反映結果に書く。追加の成否が不明なときは、親を確かめ直して決める。
  - 追加: 404 で `No parent issue found` が返った。修正 Issue の数値の `id` を使って追加する。
  - 追加済み: 親が `SUMMARY_NUMBER` だった（同じ実行の再開など）。
  - 親あり: 親が別の Issue だった（過去の監査の集約 Issue など）。付け替えず、親の URL を書く。
  - 失敗: ほかのエラーが返った、または追加できなかった。理由を書く。

  ```bash
  ID=$(gh api --hostname "$REPO_HOST" "repos/$REPO/issues/$NUMBER" --jq .id)
  gh api --hostname "$REPO_HOST" -X POST "repos/$REPO/issues/$SUMMARY_NUMBER/sub_issues" -F sub_issue_id="$ID"
  ```
